Why is this an issue?

Creatio server code (entity event listeners, configuration web services, process script tasks, business rules) frequently encodes business thresholds: a maximum price, a retry count, a discount ceiling, an expiry window, a status Guid. When such a value is written directly into the C# source as a literal, changing it stops being a configuration act and becomes a development act.

A hard-coded threshold forces the whole deployment cycle for what should be a one-field edit:

  • edit source → rebuild the package assembly → reload the package → restart the application;
  • every environment (dev, test, prod) is locked to the same number, so a tenant or region cannot differ;
  • the number cannot be adjusted per user, role or organisation, which SysSettingsValue supports natively;
  • administrators lose the audit trail and the change history that the System settings section provides;
  • the same constant tends to get duplicated into a validation message, a client-side rule and a report, and the copies drift apart silently.

The correct home for a business threshold is a Creatio system setting (SysSettings), read at runtime through Terrasoft.Core.Configuration.SysSettings.GetValue<T>.

The three bindings this rule enforces

"Use a system setting" is only half the fix. A setting that the code reads but the package never ships silently evaluates to its default, and the validation quietly stops working. The value is only correctly externalised when all three bindings below hold. The rule reports whichever one is missing.

  1. Value bound to a setting. The threshold operand must originate from SysSettings.GetValue<T>(userConnection, code, fallback) — not from a numeric or Guid literal, and not from a const holding the number itself.
  2. Code bound to a named constant. The setting code passed to GetValue must be a private const string field, not an inline string. Inline codes get copy-pasted and typo'd, and a typo'd code silently returns the fallback instead of failing.
  3. Setting bound to the package. A folder Data/SysSettings_<Code>/ (plus its SysSettingsValue_<Code>/ default) must exist in the same package, so installing the package creates the setting. Code that reads a setting no package installs is a latent defect, not configuration.

Because GetValue returns the fallback when the setting is absent or blank, the code must also handle the unconfigured case explicitly rather than letting a 0 fallback act as a real threshold — a 0 maximum would reject every record.

How to fix it

Create the system setting in the package's Data folder, hold its code in a const string, read it through SysSettings.GetValue<T>, guard the unconfigured case, and let the localizable message take the value as a {0} placeholder instead of repeating the number in prose.

Noncompliant code example

[EntityEventListener(SchemaName = "UsrYacht")]
public class YachtEntityEventListener : BaseEntityEventListener
{
    public override void OnSaving(object sender, EntityBeforeEventArgs e) {
        base.OnSaving(sender, e);
        Entity yacht = (Entity)sender;
        decimal price = yacht.GetTypedColumnValue<decimal>("UsrPrice");
        if (price > 100000) {                                  // Noncompliant - hard-coded threshold
            e.IsCanceled = true;
            string messageTemplate = new LocalizableString(yacht.UserConnection.ResourceStorage,
                "UsrYachtEvents", "LocalizableStrings.ValueIsTooBig.Value").ToString();
            throw new Exception(string.Format(messageTemplate, "100 000 EUR")); // Noncompliant - value restated
        }
    }
}

Moving the literal into private const decimal MaxPrice = 100000m; does not resolve the issue: the value is still baked into the assembly and still requires a rebuild to change. The constant must hold the setting code, never the threshold itself.

Compliant solution

[EntityEventListener(SchemaName = "UsrYacht")]
public class YachtEntityEventListener : BaseEntityEventListener
{
    // Float system setting holding the maximum allowed yacht price.
    // A non-positive value means the limit is not configured, so the check is skipped.
    private const string MaxPriceSettingCode = "UsrYachtMaxPrice";

    public override void OnSaving(object sender, EntityBeforeEventArgs e) {
        base.OnSaving(sender, e);
        Entity yacht = (Entity)sender;
        decimal maxPrice = Terrasoft.Core.Configuration.SysSettings.GetValue<decimal>(
            yacht.UserConnection, MaxPriceSettingCode, 0m);
        if (maxPrice <= 0) {
            return;                                             // Setting is not configured.
        }
        decimal price = yacht.GetTypedColumnValue<decimal>("UsrPrice");
        if (price <= maxPrice) {
            return;
        }
        e.IsCanceled = true;
        string messageTemplate = new LocalizableString(yacht.UserConnection.ResourceStorage,
            "UsrYachtEvents", "LocalizableStrings.ValueIsTooBig.Value").ToString();
        throw new Exception(string.Format(messageTemplate, maxPrice));
    }
}

Shipped alongside it, so the setting exists after install:

packages/UsrYacht/Data/SysSettings_UsrYachtMaxPrice/data.json         <- Code "UsrYachtMaxPrice", ValueTypeName "Float"
packages/UsrYacht/Data/SysSettingsValue_UsrYachtMaxPrice/data.json    <- default FloatValue 100000.00

And the message text carries a placeholder rather than the number:

<Item Name="LocalizableStrings.ValueIsTooBig.Value" Value="No yacht should cost over {0:N0}" />

Exceptions

No issue is raised for:

  • the identity and neutral values -1, 0, 1, and Guid.Empty, which are sentinels rather than thresholds;
  • comparisons against Count, Length, Rows.Count and similar collection sizes, and against string.Empty;
  • technical constants that are not business policy: HTTP status codes, buffer sizes, array indices, TimeSpan unit conversions, and units of measure;
  • generated code under packages/*/Autogenerated/**, and test code under tests/**, where fixed expected values are the point.
